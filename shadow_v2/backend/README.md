# Dedicated private backend (not deployed)

Use a newly created Supabase project dedicated to shadow v2. Do not run this migration in a v1 or shared project. `001_private.sql` creates an isolated schema, RLS on every table without client policies, explicit PUBLIC/anon/authenticated revocation, and one service-role-only RPC. No browser receives the service role. Cloud acceptance is blocked until this migration and authenticated integration scenarios pass against that dedicated project.

Deploy `index.ts` as function `memo-v2` with JWT verification disabled because it authenticates independent high-entropy opaque tokens through the private RPC. Configure `V2_ALLOWED_ORIGIN` to exactly the review site's origin (no trailing path or wildcard). Supabase supplies `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` only to the function. Do not log request headers or bodies. CI has no browser Origin; Origin-bearing CI requests are rejected.

Generate each token with Python `secrets.token_urlsafe(32)` in a private administrative session. Store only its SHA-256 hexadecimal digest in `memo_v2.tokens(hash,reviewer,role)`, with distinct tokens for each reviewer and for CI. `role` is `reviewer` or `ci`. Save the raw reviewer token in a password manager/private fragment link and the raw CI token as `V2_CI_TOKEN` in the isolated repository environment. Never paste raw tokens into SQL, source, logs or query strings. Token creation/revocation is an administrative database operation, not an exposed RPC operation. Rotate by creating a new digest and revoking the previous row (`revoked=true`) in one administrative transaction. SQLite equivalents are `Store.create_reviewer_token`, `rotate_token`, `revoke_token`; the caller must protect any displayed raw token.

The CI Python adapter takes `(endpoint, token)` where endpoint is `https://<dedicated-project>/functions/v1/memo-v2`. Use `V2_BACKEND_URL` and `V2_CI_TOKEN`. It sends POST `{action:'ci',operation,arguments}`; allowed operations are register_edition, latest_edition, get_item, get_item_feedback, get_preference_profile, save_preference_profile, save_shadow_run, add_embedding, has_embedding, search_history. Neither role can create/revoke tokens through this endpoint. Reviewer tokens cannot execute CI operations; CI tokens cannot execute reviewer operations. Research tools should restrict their own exposed operation set to reads.

Reviewer transport: `Authorization: Bearer <token>`; GET `?action=edition` yields `{edition,labels}` scoped to that reviewer. POST JSON `{action:'feedback',item_id,label,client_event_id,edition_id}` yields `{saved:true,client_event_id,label}`. Labels are `used`, `not_relevant`, `cleared`. UUID event IDs are immutable and unique; identical retries are accepted, conflicting retries rejected. Reviewer identity is derived server-side. Edition membership is enforced by foreign key, with at most 60 new events per reviewer per minute. Latest labels use server insertion sequence; cleared resolves to unlabeled. A new event from another device arriving later wins even if created offline earlier. Public uncredentialed visitors cannot retrieve editions or feedback from this private service.

Before activation, run the SQLite and Edge tests and then actual dedicated-cloud tests: migrate SQL; confirm anon/authenticated cannot access schema/RPC; seed two reviewers plus CI; test missing/wrong/revoked tokens, cross-role denial, two-reviewer isolation, event replay/conflict, edition mismatch, undo, rate boundary, vector1536 model/version/date/ticker/topic filtering, run/profile persistence, token rotation, CORS, and failure without secret-bearing responses. Neither fixture tests nor migration inspection proves cloud readiness. The exact migration and every RPC are now executed by `npm --prefix shadow_v2 run test:sql` against actual PostgreSQL/pgvector in PGlite (pinned 0.5.8 with pglite-pgvector 0.0.9). This suite also checks permissions, malformed replay, vector validation, normalized revisions, and EXPLAIN index use. Hosted Supabase/PostgREST/Deno and concurrent-worker behavior still require dedicated deployment validation.

History vectors inform preferences and duplicate checks, never current facts. SQLite permits test vectors of other dimensions; the OpenAI adapter and cloud table require 1536 dimensions. The SQLite fallback examines at most the newest 5000 model/version/date-matching embeddings; cloud retrieves at most 200 candidates using direct cosine-distance HNSW order before weighted recency reranking, with a maximum 50 returned entries. Model/version/date/ticker/topic predicates apply to candidate selection using private embedding metadata. Iterative HNSW uses ef_search=200 and max_scan_tuples=5000 (an approximate scan bound in pgvector, not an exact work counter). This approximate retrieval can return fewer matches for selective filters; it is never an exhaustive current-fact search. EXPLAIN regression verifies the exact shipped candidate SELECT uses embeddings_hnsw. Raw imports do not call an embedding API. The parser uses a versioned conservative keyword tagger for topics/sectors and six known company aliases, and extracts only explicit ticker strings; absent research cutoff stays empty. These metadata tags are retrieval aids, not verified current facts. Retrieval ranks 90% cosine relevance plus 10% recency.

Formatting-only source revisions retain their shared normalized item identity; each edition stores its own exact raw Markdown body for copying. The shared item record remains its first presentation, and body hash checks validate canonical content. Zero/near-zero, nonnumeric, nonfinite and out-of-bound vectors are rejected before insert/query. Accepted vectors are normalized with bounded float64 arithmetic before conversion to pgvector float32 and before SQLite storage/query, preventing cosine overflow/underflow for admitted extreme magnitudes. Boundary regression tests include all1536 coordinates at 1e18,1e19,1e20 and small accepted scales; all yield finite self-distance and ranking. `has_embedding(item_id,model,version)` returns true only for an exact current body-hash match, allowing CI to skip already indexed items safely. It remains unavailable to reviewer tokens.

One-off historical backfill (separate from latest-publication sync): run `python -m shadow_v2.ingest --public-archive /explicit/public/memos --cloud --max-editions 100 --source-version archive-v1` with the dedicated `V2_BACKEND_URL` and `V2_CI_TOKEN` already configured privately. Alternatively use `--store /private/outside-repository/history.sqlite` instead of `--cloud`; the options are mutually exclusive. The importer deterministically selects the newest N `memo-YYYY-MM-DD.md` files and registers them oldest first, bounded to1..1000 editions (default100). It validates the selected batch before writes, limits each source to2MB, preserves source-version provenance, and safely retries edition registrations after partial transport failure. Import creates no embeddings or feedback; newly imported items remain unlabeled. Existing explicit feedback is preserved. Archive dates are source metadata and do not establish publication timing or actual adoption. Run the separate explicit incremental embedding command after backfill when desired.

Selection snapshots use a separate authenticated reviewer action: POST JSON `{action:'selection',edition_id,selected_item_ids:[...],client_event_id:<UUID>}`. The server derives reviewer identity. `selected_item_ids` is an ordered unique array of0..100 members of that edition; an empty array clears the current selection. The receipt is `{saved:true,client_event_id,selected_item_ids}`. Exact event retries succeed; changed replays, wrong membership and malformed snapshots reject. Feedback and selection share a60-new-events/minute/reviewer limit; exact retries remain allowed. GET edition now also returns `selected_item_ids` from only the authenticated reviewer's latest snapshot of that edition. Snapshots are append-only, private, and do not alter explicit feedback labels.

The scoped CI read operation `get_selection_signals(item_ids,reviewer=None)` returns `{item_id:{selected:boolean,position:number|null,selection_count:number}}`. It consults only the latest snapshot per reviewer/edition date across same-day source revisions; position is zero-based from the newest currently active positive snapshot. Selection count is informational, not a ranking weight: repeated checkbox toggling never increases the number of active snapshots. Omitted or cleared selections mean absent weak-positive evidence, never a negative label. Optional reviewer filtering is available only to trusted CI/research callers; browser reviewers cannot call CI methods or retrieve another reviewer's snapshots. Successful-copy positive feedback continues using the existing `used` label, separately from these weaker selection signals.

`001_private.sql` now includes the private selections table, indexes and RLS/ACLs. It remains an initial migration for the dedicated backend that has not been deployed; do not reapply it over an existing deployment. A future already-deployed instance would need a separately reviewed forward migration.

A new same-day revision snapshot supersedes that reviewer's earlier revision snapshots, including an empty clear. Prior-day selections remain separate historical evidence. Absence of any new snapshot is not inferred negative feedback.

Both feedback and selection now acquire the same canonical event-UUID transaction lock before the reviewer-rate lock and cross-table replay checks. The two-integer event-lock namespace is separate from the64-bit reviewer namespace; event hash collisions only serialize otherwise unrelated events. Tests assert both guard orders and inspect actual PostgreSQL `pg_locks` for each path; this does not prove a hosted multiworker race test. The CI `get_item_feedback(item_ids,reviewer=None)` operation also supports reviewer filtering, matching `get_selection_signals`, so a configured target reviewer's preferences can be read without aggregate fallback.
